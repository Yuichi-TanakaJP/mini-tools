# 2026-08-08 ルーティン可視化を「静的な棚卸し」にする

## 背景

「毎日の X 投稿、自動でやっているデータ取得、手動でやっているデータ取得を
カレンダーで見て、自分がどれくらい作業しているか可視化したい」という要望から検討した。

### なぜ可視化したいのか

**毎日かなりの情報量を浴びているので、現状を把握して対策を立てるため。**

つまりこのツールの目的は「作業をこなした記録を残すこと」ではなく、
**流入している情報とその処理コストの現状把握** にある。減らす・まとめる・自動化するといった
対策の判断材料になることがゴールで、可視化そのものが目的ではない。

この目的があるため、後述の判断は次の基準で選んでいる。

- 記録を貯めることより、**総量と偏りが一目で分かること**を優先する
- 新しく継続的な入力負担を増やさない（対策を立てる前に運用が破綻しては本末転倒）

当初はチェックイン式の活動ログ（日々つけて GitHub 草のように貯める）を想定したが、
検討の結果「日々つけたいのではなく、**いま回しているものを一覧したい**」であることが分かった。

## 決定

### 1. 実行ログではなく静的な棚卸しにする

- 日々の記録機能（チェックイン、連続日数、実績カウント）は **作らない**
- 定義は `app/premium/routines/data/routines.ts` にハードコードし、棚卸し時に手で更新する
- 保存先を持たない（LocalStorage も使わない）

理由:

- 目的は「自分がどれくらい作業しているか」の把握であり、
  ルーティンの設定内容が分かれば総量は計算できる。日々の記録は不要。
- 記録機能を持つと入力を続ける負担が発生し、途切れた時点で価値が落ちる。
- 実行実績の自動取り込みは、別プロジェクト（`market_info` / GCP `market-info-api`）側に
  ジョブ履歴エンドポイントを新設する作業が必要になり、範囲が跳ね上がる。

### 2. 表示は週間タイムテーブル

- 縦軸 = 時刻、横軸 = 月〜日のグリッドにする
- 月次・不定期は下に別セクションとして置く

理由:

- 実データが「毎日 10 本 / 平日のみ 3 本 / 週次 4 本」の構成で、**時間帯の偏り**
  （朝 06:10〜06:35 に 3 本、08:00 に 3 本、夜 20:00〜21:30 に 5 本が集中）が
  作業実感の中心だった。
- 月カレンダー（1マス=1日）は毎日実行のものが全マスに出て冗長になる。
- カテゴリ別リストは一覧性は高いが、時間帯の密度が読み取れない。

### 3. 掲載範囲はリポジトリ横断で全部載せる

`mini-tools` に限定せず、`market_info` / `test_line_news` / `portfolio_x_post` /
`claude-skills` のルーティンも載せる。

理由: 目的が「自分の作業総量の把握」なので、リポジトリ境界で切ると総量が見えない。

### 4. 公開ツール一覧には載せない

- `lib/tools-catalog.ts` に登録しない
- `app/sitemap.ts` に追加しない
- `metadata.robots` を `index: false, follow: false` にする

理由:

- 個人の作業内容の棚卸しであり、一般利用者に価値がない。
- 認証情報などの機微は含まないが、公開の既定値としては伏せる側に倒す。

必要になればカタログ登録は 1 行で足せるので、後から可逆に変えられる。

### 5. mode は auto / semi / manual の 3 分類

実態として「リマインダーが飛んできて自分で実行する」ものが 3 件あり、
自動とも手動とも言えないため中間の `semi` を設けた。

## 棚卸し結果（2026-08-08 時点）

| mode | 件数 | 主な内容 |
|---|---|---|
| auto | 14 | 経済指標・EDINET・TDnet・投資部門別・優待/決算/JPX マスタ、LINE 通知系 |
| semi | 3 | 信用在庫（日興・SBI）、月次ランキング |
| manual | 11 | market ランキング取得、優待購入銘柄チェック、SBI 配当入金チェック、X 投稿（日次・週次・プレビュー・優待レポ）、note、開発運用スキル |

週あたり 96 回、月あたり 4 回。

### 初回棚卸しで漏れた手動 job

タスクスケジューラとスキル定義だけを見たため、**スケジューラに載らない手動 job を取りこぼした**。

- **market ランキング取得（`run_naito_and_backup.ps1`）** — 平日 20:00。
  内藤証券のログインと 2FA を手で処理する必要があり、そもそも無人実行できないため
  スケジューラに存在しない。株価ランキング / 日経225寄与度 / TOPIX33 / 米国株ランキングの
  publish まで担う日次運用の主軸で、mini-tools の表示データの大半がここから来る。
- **優待の購入銘柄チェック / SBI 配当の入金チェック** — 平日 08:00（寄り付き前）。
  証券会社サイトの目視確認でコードを伴わないため、リポジトリ内に痕跡がない。

教訓: **自動化されていない作業ほどリポジトリに痕跡が残らない。**
棚卸しの出所にはスケジューラとスキル定義に加えて
`market_info/docs/operations/{daily,monthly}_operations.md` と本人への確認を含める。
実行頻度と時刻もコードからは分からないため、本人に確認して埋めた。

なお、コードを伴わない目視確認は `repo` を持たないため、`Routine.repo` は optional にした。

## 今後の選択肢（今回は採らない）

「情報量の現状把握と対策」という目的に近い順に並べる。

- **1件あたりの情報量・処理コストの記録**（例: LINE 通知の本数、目を通すのにかかる時間）。
  現状は「実行回数」しか持っておらず、回数と浴びる情報量は比例しない。
  対策を立てるには、どのルーティンが重いかが分かる指標が要る。
- **対策後の再棚卸し**。減らした・まとめた結果を同じ画面で比べられるように、
  棚卸しの履歴（過去の `ROUTINES_SURVEYED_ON` 時点の定義）を残すことも考えられる。
- 実行実績の自動取り込み（`market_info` 側にジョブ履歴 API を新設する前提）。
  ただし「設定どおり動いたか」の確認であり、上記の目的とは直結しない。
- ホームのツール一覧への掲載
